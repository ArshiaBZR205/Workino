## ۱. مقدمه

### ۱.۱ هدف سند

این سند معماری نرم‌افزار پروژه ورکینو را تعریف می‌کند.
هدف آن مشخص کردن ساختار کلی سیستم، لایه‌های اصلی و نحوه ارتباط بخش‌های مختلف است.

### ۱.۲ دامنه

- **در دامنه:** معماری کلی سیستم، لایه‌ها، ارتباط بخش‌ها و امنیت.
- **خارج از دامنه:** جزئیات پیاده‌سازی و کدنویسی.

### ۱.۳ ذی‌نفعان

| ذی‌نفع | نقش |
|---|---|
| تیم توسعه | طراحی و پیاده‌سازی سیستم |
| استاد درس | ارزیابی پروژه |
| مشتری | ثبت درخواست خدمات |
| متخصص | ارائه خدمات و ارسال پیشنهاد قیمت |
| مدیر سایت | مدیریت و نظارت بر سیستم |

## ۲. نمای کلی معماری

### ۲.۱ سبک معماری

**Monolith + Layered Architecture**

در این معماری، سیستم به‌صورت یک برنامه واحد طراحی می‌شود و از سه لایه اصلی تشکیل شده است:

- Presentation Layer
- Business Layer
- Data Layer

این معماری برای پروژه‌های کوچک و تیم‌های توسعه محدود مناسب است.

### ۲.۲ دیاگرام لایه‌ها

┌─────────────────────────────────────┐
│         Presentation Layer          │
│       رابط کاربری و صفحات سایت       │
└──────────────────┬──────────────────┘
                   │
                   ▼
┌─────────────────────────────────────┐
│          Business Layer              │
│       منطق و قوانین سیستم            │
└──────────────────┬──────────────────┘
                   │
                   ▼
┌─────────────────────────────────────┐
│            Data Layer                │
│          PostgreSQL                  │
└─────────────────────────────────────┘

### ۲.۳ جریان داده

1. کاربر از طریق رابط کاربری با سیستم ارتباط برقرار می‌کند.
2. درخواست کاربر به لایه منطق سیستم ارسال می‌شود.
3. لایه منطق، اطلاعات موردنیاز را از دیتابیس دریافت یا در آن ذخیره می‌کند.
4. نتیجه عملیات به رابط کاربری بازگردانده می‌شود.

---

## ۳. لایه‌های معماری

### ۳.۱ Presentation Layer

این لایه مسئول نمایش صفحات و دریافت اطلاعات از کاربران است.

وظایف:
- نمایش صفحه ثبت‌نام و ورود
- نمایش پروفایل متخصصان
- جست‌وجوی متخصصان
- ثبت درخواست خدمات
- نمایش پیشنهادهای قیمت
- نمایش وضعیت درخواست‌ها

### ۳.۲ Business Layer

این لایه مسئول اجرای منطق و قوانین اصلی سیستم است.

وظایف:
- مدیریت حساب مشتریان و متخصصان
- بررسی اطلاعات ورود کاربران
- مدیریت درخواست‌های خدمات
- مدیریت پیشنهادهای قیمت
- مدیریت شکایت‌ها
- مدیریت نظرات و امتیازها
- ارسال اعلان به متخصصان

### ۳.۳ Data Layer

این لایه مسئول ذخیره‌سازی و بازیابی اطلاعات سیستم است.

**DBMS انتخاب‌شده: PostgreSQL 16**

اطلاعات اصلی ذخیره‌شده شامل موارد زیر است:

- اطلاعات مشتریان
- اطلاعات متخصصان
- اطلاعات مدیران
- دسته‌بندی خدمات
- درخواست‌های خدمات
- پیشنهادهای قیمت
- نظرات و امتیازها
- شکایت‌ها
- اعلان‌ها
- زمان‌های در دسترس متخصصان

## ۴. تصمیم‌های معماری (ADR)

### ADR-01: انتخاب معماری Monolith

**تصمیم:** استفاده از معماری Monolith

**دلایل:**
- مناسب بودن برای تیم کوچک
- سادگی طراحی و پیاده‌سازی
- مدیریت آسان‌تر بخش‌های مختلف
- نیاز نداشتن به راه‌اندازی چند سرویس مستقل

### ADR-02: انتخاب PostgreSQL

**تصمیم:** استفاده از PostgreSQL برای دیتابیس

**دلایل:**
- پشتیبانی از دیتابیس رابطه‌ای
- پشتیبانی از کلیدهای اصلی و خارجی
- مدیریت ارتباط بین جدول‌ها
- رایگان و متن‌باز بودن

## ۵. REST API

در این بخش مسیرهای اصلی ارتباط رابط کاربری با بخش منطق سیستم مشخص شده‌اند.

### ۵.۱ Endpointهای عمومی

| Method | Endpoint | توضیح |
|---|---|---|
| GET | /api/specialists | مشاهده لیست متخصصان |
| GET | /api/specialists/:id | مشاهده جزئیات متخصص |
| GET | /api/categories | مشاهده دسته‌بندی خدمات |
| GET | /api/specialists/search | جست‌وجوی متخصصان |

### ۵.۲ Endpointهای مشتری

| Method | Endpoint | توضیح |
|---|---|---|
| POST | /api/requests | ثبت درخواست خدمات |
| GET | /api/requests | مشاهده درخواست‌های مشتری |
| GET | /api/requests/:id | مشاهده جزئیات درخواست |
| GET | /api/requests/:id/quotes | مشاهده پیشنهادهای قیمت |
| POST | /api/complaints | ثبت شکایت |
| POST | /api/reviews | ثبت نظر و امتیاز |

### ۵.۳ Endpointهای متخصص

| Method | Endpoint | توضیح |
|---|---|---|
| GET | /api/specialist/requests | مشاهده درخواست‌های مرتبط |
| POST | /api/quotes | ارسال پیشنهاد قیمت |
| PUT | /api/specialist/profile | ویرایش پروفایل متخصص |
| GET | /api/notifications | مشاهده اعلان‌ها |

### ۵.۴ Endpointهای مدیر سایت

| Method | Endpoint | توضیح |
|---|---|---|
| GET | /api/admin/users | مشاهده کاربران |
| PUT | /api/admin/users/:id | مدیریت حساب کاربری |
| GET | /api/admin/complaints | مشاهده شکایت‌ها |
| PUT | /api/admin/complaints/:id | تغییر وضعیت شکایت |
| POST | /api/admin/categories | ایجاد دسته‌بندی |

### ۵.۵ نمونه Response

نمونه اطلاعات یک متخصص:

~~~json
{
  "id": 1,
  "full_name": "علی رضایی",
  "skills": "تعمیرات کامپیوتر",
  "service_area": "تهران",
  "estimated_rate": 500000
}
~~~

## ۶. امنیت

### ۶.۱ احراز هویت

- کاربران برای ورود به حساب خود باید احراز هویت شوند.
- گذرواژه‌ها باید به‌صورت هش‌شده ذخیره شوند.
- اطلاعات حساب کاربران باید محافظت شوند.

### ۶.۲ مجوزدهی

دسترسی کاربران بر اساس نقش آن‌ها مشخص می‌شود.

نقش‌های اصلی:
- Customer
- Specialist
- Admin

### ۶.۳ امنیت اطلاعات

- جلوگیری از دسترسی غیرمجاز به اطلاعات کاربران
- بررسی اطلاعات ورودی کاربران
- محدود کردن دسترسی به بخش مدیریت
- استفاده از ارتباط امن در محیط عملیاتی

## ۷. مقیاس‌پذیری

### ۷.۱ محدودیت‌های فعلی

- معماری Monolith برای پروژه‌های بسیار بزرگ ممکن است محدودیت ایجاد کند.
- افزایش تعداد کاربران می‌تواند نیازمند منابع سخت‌افزاری بیشتر باشد.

### ۷.۲ مسیر توسعه

در صورت افزایش کاربران و گسترش پروژه، امکان توسعه و بهبود معماری وجود دارد.
